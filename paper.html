Shared Presents

One transcript, many holograms, and abilities named by the record

A saved conversation names, turn by turn, exactly which agent files were loaded. Any surface can load the same file and stand where that conversation stood: replay it, fork it, or let several AI speakers share it, each answering with only its own abilities.

Part 4 of Frame Chains → Living Holograms → Thought Contracts → Shared Presents.

Kody Wildfeuer · RapterBox LLC · First public disclosure: 2026-11-19

In one sentence: when each turn of a saved conversation names the exact, fingerprinted agent files it ran with, the conversation itself becomes the hologram's shape at every moment, so it can be replayed byte for byte, forked from any turn, moved between surfaces with nothing changed, and shared by several speakers who load and unload their own abilities as their turn comes.

The short version

  • The record names the abilities. Thought Contracts showed that what is in the agents folder is what the hologram can do. Here the conversation decides what is in the folder: each turn carries a list of agent fingerprints, and loading that turn makes the folder hold exactly those files.
  • Unloading is free. Anything the next turn does not name is gone for that turn. Presence is ability, and the record now governs presence.
  • Stacks. A stack is a named list of exact agent versions plus static routes. Words in the last few turns pick child stacks the same way every time. The same stack and the same words load the same agents.
  • Time travel. Because every version is kept by fingerprint, turn 7 of an old conversation can be replayed with the agents of that moment, not today's. A fork from any turn names its parent.
  • A shared present. Several speakers in one transcript, each turn naming its speaker's stack: one runtime, one file, and the hotload mechanic is the whole engine. This answers the question Part 3 ended on.
  • The agent file stays sacred. A stack may optionally travel as one ordinary agent file that unpacks its members after checking each fingerprint.

1 · Where the series left off

Frame Chains [1] made the history of an estate verifiable without trusting a clock. Verified Frame Worlds [2] made an application's visible state a replay of its record, with forks that name their parent frame. Living Holograms [3] made that history steerable through lenses: agent files whose identity is the hash of their source, so editing one description makes a new lens. Thought Contracts [4] showed that a hologram's abilities are plain files read fresh on every turn: a file arrives and the next turn can do more; a file leaves and the ability goes. It closed with a question: what happens when two holograms share one present?

Two gaps remained in practice. First, which files were present at a given turn was a fact about one machine's folder, not about the conversation. Move the conversation to another machine, or come back next month, and the folder holds something else. Second, a hologram with thousands of possible abilities cannot show them all to a model at once, and choosing a subset by hand does not repeat.

This paper closes both with one move: the conversation names its abilities.

2 · Design

2.1 Three words

The design uses three nouns, each mapped to one that already exists in RAPP:

WordWhat it is
AgentOne agent.py file: one tool, a description, described parameters and a perform(). Its identity is its file name plus the tool name it registers; each version is kept by its SHA-256.
StackA named folder of references, never copies: exact agent versions by fingerprint, child stacks, and static routes. It has a stable identifier.
SkillA skill.md page an AI reads and carries out, which names the stack it needs. An agent file is never called a skill.

2.2 A catalog by fingerprint

Every agent version an estate has ever run is kept once, under its fingerprint, in a local catalog. Nothing is overwritten; a new version is a new entry beside the old one. This is the rule Git applies to file contents and Nix to packages: you cannot replay yesterday with today's code.

2.3 The record names the folder

The chat file that the Brainstem already exports gains one field per turn: the list of agent fingerprints that turn ran with, and the stack it came from. Loading a turn means: resolve the stack, fetch each named file from the catalog, re-hash it, and make the folder hold exactly those files. If any file is missing or its hash differs, the turn is refused whole. A turn is never half-loaded. An older chat file without the field loads as it always did.

2.4 Static routes

A stack may carry routes: a list of words and the child stack each one selects. The words of the last four turns, lowercased and split into whole words, are matched against them. The rule is deterministic, so the same stack and the same conversation choose the same agents on every machine. One stack identifier can therefore take many shapes, chosen by what is being talked about, while every shape remains reproducible. The model sees only the handful of agents a turn routes to, never the whole catalog.

2.5 Time travel and forks

Replaying turn k loads what turn k named. An upgrade to an agent changes the answers of new conversations and leaves pinned old ones untouched. A fork copies turns 0 to k, records the parent conversation's hash and the turn it left from, and continues; its shared prefix replays byte for byte. This is Verified Frame Worlds' prefix rule applied to abilities rather than to board state.

2.6 A shared present

A group conversation is one transcript in which each turn names a speaker and that speaker's stack. Before a speaker answers, its stack is loaded; when the next speaker's turn comes, that set is unloaded and the next one loaded. Every speaker reads the whole transcript as its present, and answers with only its own abilities. No new runtime is needed: one Brainstem and one file carry the whole group, and each turn records who spoke with which agents.

In Thought Contracts' terms, the transcript is the shared structure that writers and readers meet in. Several holograms share it, and none calls another.

2.7 The record names its data too

Abilities are half of a present. The other half is what the caller is shown. Large material (tables, full call quotes, long lists) is kept beside the transcript by fingerprint, as agents are, and never pasted into it. Each turn names the pieces it pulls back, so the next caller sees exactly what that turn pulled and nothing else; a piece no turn names is absent. A pulled piece whose bytes no longer match its fingerprint refuses that turn whole, exactly as a changed agent does. With both halves named, replaying a turn gives the caller the same tools and the same facts, and the transcript stays small because both ride by reference. This is Living Holograms' data sloshing, with the carried material addressed rather than retold.

2.8 One file when it must travel

A stack can optionally be exported as a single ordinary agent file, in the shape of the factory agents already published in RAR [6]. It carries its members with their fingerprints and, when asked to install, checks each one before writing it beside itself; if a different file of the same name is already there, it keeps the owner's file and says so. The single agent file remains the one unit everything ships as.

3 · Reduction to practice

The proof. One self-contained page holds a seven-turn conversation between a person and three AI speakers, five agent versions and five stacks, with real SHA-256 from the browser. Seal records each turn's agents and answer hash. Replay compares. Upgrade, fork and tamper show what each does. A dependency-free Node check, node scripts/check.mjs, runs the same core and passed 14 of 14 on 2026-11-19:

  • every turn replays to its sealed answer, 7 of 7;
  • each turn loads exactly the agents it names, routed by the last four turns;
  • the speaker on turn 4 holds only its own agent, and the agents of turns 0 to 3 are gone;
  • an upgrade changes the answer for a new conversation, while the old one, replayed with what it named, is unchanged;
  • a fork at turn 3 keeps turns 0 to 3 byte-identical and names its parent;
  • one byte added to one agent refuses every turn that names it, and leaves the other turns replaying;
  • a turn that pulls a data piece by fingerprint replays with it, and one character added to that piece refuses that turn only, while the other 6 replay. Removing the piece check turns this red.

Driven headlessly at phone width, the page gave 7 of 7 on replay, refused the 3 turns that name the tampered agent, and showed no errors.

On a live estate. On the author's laptop, a local catalog holds 155 agent identities with every version by fingerprint. Saved chat files with the agents field load the agents they name and unload the rest; three of three saved chats loaded their named sets after the catalog was re-keyed. A stack tree, routes (five of five test sentences), and the single-file export (four of four members byte-identical to the catalog) each ran once.

Per-chat folders and a live group conversation (added later on 2026-11-19). On the author's own runtime, each conversation now loads into its own folder; three conversations asked at the same moment each listed only their own agents (3 of 3). A live group conversation with a person and three AI speakers ran once: each speaker loaded only its own stack, two called their own tools, and the third, which held only a browser agent, said it could not check disk space (3 of 3).

What does not exist yet. Replay against a live model is not byte-identical, because the model is not; what replays exactly is which abilities and data it had. Data pieces by fingerprint run in the proof, not yet on the live estate. Other machines do not yet pull from the catalog by fingerprint.

4 · Related work

Each part has an ancestor. Content-addressed storage with immutable history is Git's; whole-system pinning and rollback by hash is Nix's [7]; replay of state from a log is event sourcing [8]. Routing tables pick handlers by fixed rules, as request routers and Unix shells do. Package lockfiles record exact versions so a build repeats. Blackboard and tuple-space systems let independent agents share one structure without calling each other [9]. The Model Context Protocol [10] lets a tool list change during a session; here the list is a property of the record instead. We claim only the combination: a conversation whose turns name fingerprinted abilities, resolved by static routes, so that it replays, forks, travels and is shared.

5 · Limitations

  • Abilities replay; answers from a model do not. The proof's agents are pure, so their answers replay byte for byte. A live model given the same abilities may still answer differently.
  • Fingerprints prove sameness, not safety. A pinned agent can be pinned and harmful. Where agents come from still needs a trust rule.
  • Routes match words. Whole-word matching misses other forms of a word; the proof uses plain words only.
  • Isolation is per folder, inside one process. Conversations get separate folders, but their agents still run in one runtime process with its permissions.
  • Identity by name and tool name. Two unrelated files with the same name and the same tool name would be treated as versions of one agent.
  • One estate, one author, runs counted once. The live results above were each run once on one laptop.

6 · Conclusion

Frame Chains made history verifiable. Living Holograms made it steerable. Thought Contracts made the hologram react to what is present. Shared Presents lets the record decide what is present. The conversation names its abilities; loading a turn makes them present and everything else absent; an old turn replays with the abilities it had; and several speakers can share one present, each with its own.
