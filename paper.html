Working Sets

A chat remembers its agents

Treat an agent runtime as an operating system. An agent file is a program. A saved chat is the launcher: it opens only the programs that ran in it, and closes them when the job is finished. Run the chat again and compare which programs ran, and you have a check that reading the replies cannot give.

Part 4 of Frame Chains → Living Holograms → Thought Contracts → Working Sets.

Kody Wildfeuer · RapterBox LLC · First public disclosure: 2026-11-19, under the title Shared Presents (that version, as published). Rewritten 2026-11-20 after a day of use.

In one sentence: a saved chat already records which agents ran, so loading only those agents, releasing them afterwards, and comparing which agents run on the next pass turns an ordinary transcript into a launcher, a way to keep unneeded tools out of reach, and a check that the same steps ran.

The short version

  • The runtime is an operating system. Agent files are programs, a catalog is the store, a saved chat is the launcher, and what is loaded right now is what is open.
  • The transcript is the record. The transcript a runtime already exports says which agents ran on each turn. Nothing has to be added for that to be true.
  • Open the working set, nothing more. Replaying a saved chat loads only the agents that ran in it, beside a small everyday set. The everyday set stays small, and apart from that set, tools the job never used are not in reach.
  • Check what ran, not what was said. If an agent ran before and does not run now, that step needs a second look: say it once more, then ask the person. In live runs this caught replies that said “saved” when nothing had been saved.
  • A refusal is a signal. “I do not have a program open for that” means look on the shelf, open what fits, do the job, close it.
  • Learned, practiced, memorized. A job done once is learned. Replayed with a matching check it is practiced. Pinned to exact versions it is memorized.

1 · Where the series left off, and what a day of use removed

Thought Contracts [4] showed that an agent runtime's abilities are plain files read fresh on every turn: a file arrives and the next turn can do more; a file leaves and the ability goes. The first version of this part, published a day earlier, built a great deal on that: named stacks of agents, word routes between them, an agent list on every turn, a folder per conversation, data pieces by fingerprint, several speakers sharing one transcript. Each piece worked when tried once.

In use, almost all of it was more than the job needed. Routing by words was a second thing to keep right. A list on every turn duplicated what the transcript already said. What survived a day of real work is one idea small enough to say aloud: a chat remembers its agents. This rewrite is about that idea, what it turns the runtime into, and what we measured when we leaned on it.

2 · Design

Four words are used throughout. The model is the language model that reads a request and decides what to do. The runtime is the small local program that passes requests to the model and runs what it chooses. An agent file is one file that gives the runtime one ability, with a plain description of when to use it. A tool is ordinary software already on the machine that an agent file may drive.

2.1 The runtime as an operating system

Once agents load and unload between turns, a runtime behaves like a small operating system driven entirely through chat. The mapping is direct, and each row is something an operating system already taught:

In an operating systemHere
A programOne agent file: one tool, a description, described inputs.
Open programsThe agent files loaded right now. The model can reach these and nothing else.
Opening and closing a programLoading agent files before a job and releasing them after it.
A shortcut that launches a programA saved chat. It names, by having used them, the programs a job needs.
A software storeA public catalog of agent files, each version kept by fingerprint [6].
“No application can open this file”“I do not have a program open for that.”

The runtime itself is not changed for this. Loading and releasing are done by one ordinary agent file that sits in the everyday set, so the operating system is built from the same unit it runs.

2.2 A chat remembers its agents

The chat file a runtime exports holds, for each turn, what was asked, what was answered, and which agents ran. That last part is usually treated as a log. Here it is the record that matters: it is a list, written by the work itself, of the programs this job used on that occasion. It is one path through the job, not every path the job could take, and it records only what ran as an agent, not everything the runtime did. Within those limits no one has to declare the job's needs in advance: doing the job once writes the list.

2.3 The working set

Denning's working set [7] is the set of pages a process has used recently, and the rule that follows: keep in memory what the process is using, and no more. The working set of a saved chat is the set of agents that ran in it. To run that job again, the runtime opens that set beside its small everyday set, does the job, and closes what it opened; the everyday set stays. An agent that was installed but never ran in the chat is not opened.

Two things follow. The everyday set stays small, so every ordinary turn carries less. And the model's choices during the job narrow: it still decides whether to call a program, which of the open ones, and in what order, but it cannot reach for a look-alike that is not open. A look-alike kept in the everyday set is still in reach, which is one more reason to keep that set small. This is in the spirit of least privilege [8], with the history standing in for a written list. It limits what the model is offered. It is not a security boundary: a loaded program can still do whatever its file does.

2.4 The check: what ran, not what was said

Run a saved chat again and there are two transcripts: the one that was saved and the new one. Comparing their wording is unreliable, because a model rarely says the same thing twice. Comparing which agents ran, step by step, is exact. There are three outcomes:

  • The same agents ran at each step. The run followed the recorded path. That is all this outcome says: it is not proof that the results are right, and a job done correctly by a different route would not match.
  • An agent ran before and did not run now. Either something the job needs is missing, or the model simply did not call it this time. The two look the same, so the move is to say the request once more and, if the step still does not run, to ask the person a question that names it.
  • A different agent ran, or the steps came in another order. The job went somewhere else and the result should not be trusted until that step is looked at.

This borrows from recording a run and checking later runs against it [9], pointed at tool use. Its value is highest exactly where reading the reply fails: a model that says it did the thing when it did not.

2.5 A refusal is a signal

With a small everyday set, the runtime will often be asked for something it has no program open for. That is the system working. The answer “I do not have that open” is the cue to look at what can be opened, open the one that fits, do the job and close it. If nothing fits, either the saved chat describes its job too narrowly or the program does not exist yet. Both are fixed where they are found, and neither needs a routing table.

2.6 Learned, practiced, memorized

The same record gives a job three stages, each one a thing that already exists rather than a new mechanism:

StageWhat has happened
LearnedThe job was done once by chat, and the chat was saved with the agents that ran.
PracticedThe saved chat was run again and the check matched.
MemorizedThe saved chat is pinned to the exact versions that ran, and any step that was done by hand is locked into an agent file that carries its own proof.

A person strengthens a job by repeating it under a check, the way a skill moves from attention to habit. Each stage leaves evidence in a file anyone can open. Whether a runtime becomes measurably more reliable this way over weeks is something we have not yet measured.

2.7 The store

If a saved chat names an agent the machine does not have, the runtime fetches it from a catalog and loads it. Each version is kept under a fingerprint computed from its contents, and a fetched file is checked against that fingerprint before it is allowed to run. The principle, that a name should fix exactly what you get, is the one Nix applies to whole software installations [10]. By design this makes a saved chat portable, provided the catalog holds the agents and the machine already has the tools they drive: another machine can acquire what the job needs on first use. This section is design; it was not exercised in the runs below.

2.8 Outside tools as programs

A local tool becomes a program by being wrapped in one agent file with five habits: it takes plain inputs only; it drives a tool already on the device and says so plainly when that tool is missing; it never overwrites, so its result is a new file beside the source; it measures its own result before saying it is finished; and it returns a receipt of what was asked, what was made and what was measured.

2.9 Who drives

The whole arrangement is driven through chat, and it stacks. A person asks an assistant; the assistant asks the runtime; the runtime opens the programs the job needs; each hop passes plain words and plain inputs. When one runtime is not enough separation, several can run side by side, each with its own open programs, like separate computers for separate duties. That last arrangement is design; we have not run it.

3 · Reduction to practice

The proof. One page and one small script, with no other dependencies, hold a shelf of six programs, two of them look-alikes, and a three-line job saved with the three programs it used. The reader can open only the working set, open everything, leave a detail out, make a reply claim work that did not happen, or open nothing, and watch the check. A dependency-free Node check, node scripts/check.mjs, runs the same engine and passed 22 of 22 on 2026-11-20, including one runtime that opens a working set beside an everyday set, does the job, closes it and is asked again. Making the comparison ignore the order of steps turns 2 of the 22 red; making it always agree turns 6 red. The chooser in the proof is a fixed stand-in for a model, so the proof repeats exactly; it shows the logic, not model behaviour.

Live runs. On the author's laptop, 2026-11-20, a real runtime with a small language model choosing the agents:

  • A fact left out. When a request omitted a detail the job needed, the agent did not run in 34 of 34 turns. In those turns the omitted detail always stopped the step. We tested one kind of omission, and the reverse does not hold, as the next line shows.
  • False alarms. With the full request and the right agent open, no agent ran in 7 of 48 turns in one scenario and in 13 of 55 replayed lines in a second, run five at a time. Saying the line once more recovered 8 of those 13; 5 of 55 still missed.
  • Said, not done. In 7 of those 13 misses the reply claimed the work (“saved”, “noted”) with nothing run. The check on what ran caught each one, and in each case a later question about that fact could not be answered.
  • Look-alikes. With two similar agents both open, the wrong one was chosen in 7 of 8 turns. With only the saved chat's working set open, across the 55 replayed lines above the first try chose the right agent 42 times, no agent 13 times and a wrong agent 0 times. These are two separate samples with different requests, not a matched comparison, and a look-alike that is not open cannot be chosen by construction; they show the size of the look-alike problem and that it did not appear, not that more jobs completed.
  • Open, use, close. Asked in plain words, the runtime listed what it could open, opened one program, did a job with it and closed it, returning to its everyday set each time (11 agents, then 12, then 11, over six such cycles).
  • A refusal, cured. Asked for a job with no program named, the runtime first declined, because what it had been told about that program was too narrow. After the saved chat was corrected to describe the program fully, the same request opened the right program and completed, with the program's own measurement passing.
  • Long work outlives its launcher. A program that starts a job taking minutes was opened, started the job and was closed; the job finished on its own. Two such jobs each produced a narrated short film in about ten minutes. We inspected eight frames of each and have not yet watched either through.

What these numbers are. They are counts from our own records of those runs. The records are not published with this paper, so a reader can rerun the proof but cannot yet rerun the live runs.

What does not exist yet. A chat cannot yet save itself as a launcher at the end of a job; that step was done by hand. Fetching from the public catalog on first use is built and was not exercised in these runs. Several runtimes side by side have not been run.

4 · Related work

Each part has an ancestor, and the names are borrowed on purpose. The working set is Denning's [7]. Giving a job only what it needs is least privilege, from Saltzer and Schroeder [8]. Checking a run against a recorded one follows the self-initializing fake [9], by analogy: here the recording is of which agents ran, and the model still chooses afresh each time. That a name should fix exactly what is fetched is the principle behind Nix [10]. The Model Context Protocol [11] lets a tool list change during a session; here the list is derived from what a past session used. We claim only the combination: the transcript as the source of the working set, loading and release done by an ordinary agent file, and a check on which agents ran as the test of a replay.

5 · Limitations

  • The live records are not public. Only the proof can be rerun by a reader.
  • The check sees which agents ran, not whether they ran well. The same agent with worse inputs still matches. Each program measuring its own result covers part of that gap, not all of it.
  • False alarms are real. Between about one in seven and one in four first tries missed with nothing wrong, and one retry did not remove them.
  • One small model, one device. The live numbers come from one laptop and one small model choosing the agents, with the second scenario run under load. Larger models may miss less; we have not measured that.
  • The judges were written by the builder. No one else has reproduced the live numbers.
  • Small counts. The largest sample here is 55 lines.
  • A fingerprint proves sameness, not safety. A pinned agent can be pinned and harmful. Where agents come from still needs a trust rule.
  • Loaded programs share one process. Opening only the working set limits what the model can reach, not what a loaded file can do.

6 · Conclusion

Frame Chains made history verifiable. Living Holograms made it steerable. Thought Contracts made a runtime react to what is present. Working Sets lets the work itself decide what is present: a chat remembers its agents, a replay opens only those, and comparing what ran, step by step, tells you whether the same steps happened or whether a step needs a second look. The first version of this part used many mechanisms to say that. This version uses one.
